# ADR-001: Архитектура MVP платформы мониторинга свиноводческих ферм

**Автор:** Роман Кукин  

---

## 1. Контекст
Перед компанией «АгроТех Х» стоит задача — повысить эффективность в сфере животноводства и по максимуму автоматизировать процессы, связанные с кормлением, безопасностью и мониторингом поголовья скота. 
Решено сделать MVP архитектуры c нуля и запустить как отдельную платформу для мониторинга скота. Сначала планируется реализовать это на ограниченном количестве ферм, а затем потенциально предлагать как SaaS-решение для других компаний — это уже выходит за рамки проектной работы.

## 3. Решение

### Описание
Платформа встраивается в существующий IT-ландшафт «АгроТех Х»: публикует метрики в корпоративную Kafka, отдаёт аналитику в ClickHouse DWH, синхронизируется с «1С:Агро» по данным кормов и поголовья. Отчёты для аналитика поступают в Power BI через DWH.

**Ключевой архитектурный принцип:** переиспользование — там, где это экономит время и деньги на MVP, но с *чистыми границами модулей*, чтобы в будущем (Task 5) можно было заменить внешние зависимости на встроенные без переписывания бизнес-логики.

Контекстная диаграмма основного варианта: [c4_option1.puml](./c4_option1.puml)

**Состав системы:**
- Центральный сервер — оркестрирует агентов, хранит агрегированные данные, предоставляет API.
- Агенты на фермах (edge) — работают offline, управляют IoT-устройствами, запускают видеоаналитику локально.
- Модуль видеоаналитики — запускает партнёрские ML-модели на edge-устройствах.

**Внешние зависимости (существующие системы «АгроТех Х»):**
- Apache Kafka — публикация метрик и событий.
- ClickHouse DWH — аналитические данные для отчётности.
- ERP «1С:Агро» — данные о кормах и нормативах поголовья.
- Power BI — визуализация отчётов для директора и аналитика.
- Корпоративный IdP — аутентификация пользователей.

**Новые внешние зависимости:**
- IoT-устройства (камеры, кормушки, поилки, датчики фильтрации воды).
- Партнёрские ML-модели (через gRPC/ONNX).
- SMS-шлюз (оповещения дежурных в offline-режиме).



### Аргументация

| Критерий                        | Обоснование                                                                                                                                              |
|---------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| Time-to-market                  | Переиспользование Kafka, DWH, Power BI сокращает разработку относительно standalone-варианта                                                             |
| TCO для MVP                     | Нет дублирования существующей инфраструктуры (брокер, хранилище, BI, auth)                                                                               |
| UX для лиц, принимающих решения | Директор и аналитик работают в Power BI — не требуется обучение новому инструменту                                                                       |
| Знание инструментов командой    | Команда уже знает инструменты и умеет их поддерживать                                                                                                    |


#### Последствия

**✅ Положительные:**
- Самый быстрый путь к MVP
- Все технологии уже используются в компании
- Данные сразу доступны в корпоративном BI и ERP без отдельной интеграции

**⚠️ Негативные:**
- Сильная связанность с существующим IT-ландшафтом «АгроТех Х»
- Путь к SaaS требует дополнительной работы

**↗️ Зависимости:**
- SLA существующих систем «АгроТех Х» (Kafka, DWH, ERP, Power BI, IdP) напрямую влияет на SLA платформы
- Доступность партнёрских ML-моделей

### 5. Риски


1. **Сильная связанность с существующими системами АгроТех Х**
   *Меры:*
   - Ввести circuit breaker и retry-логику на всех адаптерах к внешним системам
   - Локальный буфер событий на агентах и на центральном сервере — агенты и платформа продолжают работать при кратковременных сбоях Kafka
   - SLA-договорённости с командами Kafka/DWH/IdP на уровне 99.99%
   - Health-checks и мониторинг зависимостей через Prometheus

2. **Сложность миграции в SaaS (Task 5)**
   *Меры:*
   - Применять hexagonal architecture (ports & adapters) с самого начала
   - Выделить чёткие интерфейсы для Kafka-publisher, DWH-exporter, ERP-client
   - Код-ревью с фокусом на утечки абстракций

3. **Offline-режим и потеря данных при длительных обрывах связи**
   При обрыве интернета на ферме более 10 минут агент продолжает накапливать события. Есть риск потери данных при переполнении буфера.
   *Меры:*
   - Persistent queue на агенте (SQLite/RocksDB) — пережить перезагрузку
   - Мониторинг размера буфера с алертами при приближении к порогу
   - Политика приоритизации событий: критичные (драки, задавливания) — отправляются первыми при восстановлении связи
